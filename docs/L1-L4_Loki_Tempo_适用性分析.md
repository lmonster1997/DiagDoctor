# L1–L4 上下文管理机制在 Loki/Tempo 日志诊断工具中的适用性分析

> 背景:借鉴 Claude Code 处理大日志的上下文管理机制(L1 snip_compact / L2 micro_compact / L3 tool_result_budget / L4 compact_history,以及子 agent 隔离上下文),评估它们在自研"基于 Loki + Tempo 的诊断 bug 工具"中是否适用、如何变形。
> 来源:一次本地 `.uihlog` 日志诊断实战的方法论复盘 + 迁移推演。

---

## 一、改变整套权衡的核心前提:数据可寻址、可无损重取

Claude Code 的 L1–L4 之所以偏"保守",是因为它处理的上下文**丢了可能不可逆**——一个命令的输出、一个运行中进程的状态,重取要么贵、要么取不回来。所以它倾向于"摘要保留信息"。

Loki/Tempo 不是这样。每条日志、每个 span 都有稳定地址(查询语句 + 时间范围 + 标签)。**丢掉上下文里的原始结果,代价是重跑一次查询,不是信息丢失。**

这一前提的推论:

- 可以比 Claude Code **激进得多地驱逐旧内容**。
- **少依赖 L4 这种有损摘要**,多依赖可重取占位。
- 这是自研工具相对裸 Claude Code 最大的结构性优势。

---

## 二、逐层映射

### L2 — micro_compact(旧工具结果占位):最该用,且能加强

收益最高的一条。一个 50 行的 LogQL 结果,替换成占位符:

```
[Loki 结果: job_id=16, 23行, 关键发现: GetImageByUID 失败 GSPS .5.1.1.1.5]
重取: {query:"...", range:[t1,t2]}
```

比 Claude Code 多出来的能力:占位符可**带查询句,一键重取**。因为数据在 DB 里,占位符天然可重水合。Claude Code 做不到这么干净,因为它的"原始结果"未必还能再取。

**设计要点**:占位符必须保留足够的重取入口(查询句、时间窗、标签),以及一行"关键发现"摘要,让后续推理不必重取也能引用结论。

---

### L3 — tool_result_budget(大结果落盘):部分溶解进 L2,但留下"贵查询缓存"形态

Claude Code 是写临时文件。这里"盘"可以直接是**查询引用本身**——L3 的职责被 L2 的可重取占位符吸收,不需要单独落盘。

但有一个 L3 的新形态值得保留:**贵查询的结果缓存**。例如 24h 的 `count_over_time` 聚合、跨服务全量 trace 拉取,重跑很贵。这种结果值得真正物化缓存,让重取是瞬时的而不是重查。

**结论**:L3 在本场景从"大输出兜底"收窄成"昂贵查询缓存",职责更窄、更明确。

---

### L1 — snip_compact(裁掉无关旧对话):适用,粒度是"调查分支"

裁掉的不是泛泛的旧对话,而是**已走死的调查分支**。一旦确认"fenix 不是失败判定侧",那条分支的详细查询结果都可裁,只留结论("fenix 排除")。

**原则:留结论,丢支撑证据。** 在 Loki/Tempo 上特别安全——证据随时可重取。

---

### L4 — compact_history(LLM 全量摘要):最危险,要约束

适用但风险最大,且因为存在重取能力,**应尽量少用**。要用时必须约束两点:

1. **摘要必须保留地址**(UID、trace ID、时间窗、查询句)。丢内容可以,丢地址=丢重取入口,那才是真损失。
2. **摘要不能是自由文本叙述**,否则会把"抢答的根因"固化进去。L4 摘要会把"根因是 X"这种未证伪的结论传到后面,污染后续判断。应结构化成 `(假设, 证据, 是否被反例否决)` 的**假设树**,而不是叙事。

> 反面案例:本次诊断中,一度把 `CalculatePixelSpacing` 异常当根因。若该结论被 L4 摘要固化传下去,后续推理会被这个未证伪假设污染。结构化假设树可避免此问题——假设树里该条会标记"未做反例检查",从而触发纠偏。

---

### 子 agent 隔离上下文:最有价值,且能落地"证伪纪律"

这是自研工具能比裸 Claude Code 多出来的核心。三种用法:

#### 1. 并行调查
一个查 fenix、一个查 zhenghe、一个查 timeout-worker,各自独立上下文,只回结论。天然契合 Loki/Tempo 多服务架构。

#### 2. 独立证伪 agent(核心)
主 agent 给出根因假设,起一个**新上下文**的子 agent,唯一任务是"在 DB 里找反例推翻它"。因上下文隔离,主 agent 已有的偏见不会泄漏进去。

这把"撞墙后回头"的被动证伪,变成**结构化的、无偏的、前置的**纠偏机制——本次诊断里"成功批 GSPS 导出也失败"这关键一刀,正是被动的、靠运气的;子 agent 隔离能把它变成确定性能力。

#### 3. 钻取 agent
主 agent 拿到 trace 树骨架,挑一个可疑 span,起子 agent 专门拉那个 span 的日志深挖,只回结论。

#### 边界
- 上下文隔离的是**会话转录**,不是工具访问。子 agent 必须共享同一个 Loki/Tempo 客户端。
- 并行子 agent 有协调成本:重复查询、遗漏跨服务关联。需一个**合成步骤**把各分支结论拼起来。
- 合成场景(A 在 fenix 发现 X、B 在 zhenghe 发现 Y,需人工连起来)正是 Workflow 的 pipeline / dedup barrier 要解决的问题。

---

## 三、两个不要踩的认知坑

### 坑一:别把"上下文管理"和"调查策略"混为一谈

- **L1–L4** 管的是*带多少上下文*。
- **对照证伪、count-first、trace 为骨架** 管的是*往哪个方向查*。

两者正交。L1–L4 做得再好,没有调查纪律,只会让 agent **高效地得出错误结论**。工具两者都要,不能只搬 L1–L4。

### 坑二:别把 L4 摘要当默认手段

Claude Code 频繁依赖 L4,是因为它很多内容不可重取。本场景有重取能力,**默认手段应是 L2(可重取占位),L4 是最后兜底**。顺序错了会把有损摘要的不准确放大。

---

## 四、Loki/Tempo 原生的压缩手段(Claude Code 没有的)

这是比 Claude Code 多出来的牌,应优先用,把 LLM 层的 L4 往后压:

### 1. 聚合即压缩
Loki 的 `sum by (component)(count_over_time(...))` 把 50 行原始结果压成 5 行聚合——这是**数据层压缩**,比 LLM 摘要便宜且无损。能表达成聚合的,绝不交给 LLM 摘要。

### 2. 查询时限量
Loki `limit`、Tempo 采样在**结果进上下文之前**就卡住大小。Claude Code 做不到(命令一旦执行,输出就是输出)。这是从源头控预算,比事后裁剪干净。

### 3. trace 树作为压缩表示
一个 200 span 的 trace 原始展开巨大,但 span 树(服务/操作/状态/耗时)是紧凑的结构摘要。正确姿势:

```
先取树骨架(便宜、紧凑)
  → LLM 挑可疑 span
  → 再拉那个 span 的日志(L3 式按需钻取)
```

这是 trace 数据原生的预算分层,L1–L4 补不出来。

---

## 五、底线结论

L1–L4 + 子 agent **都适用**,但映射后取舍重心会从 Claude Code 的"保守保信息"移到本场景的"激进驱逐 + 重取兜底"。

按优先级:

| 层级 | 在本工具中的定位 |
|---|---|
| **L2(可重取占位)** | 支柱之一。默认手段,带查询句可一键重水合。 |
| **子 agent 隔离** | 支柱之二。尤其"独立证伪 agent",把被动证伪变成确定性能力。 |
| **L1(裁调查分支)** | L2 的自然延伸,留结论丢证据。 |
| **L3(贵查询缓存)** | 收窄为"昂贵查询物化缓存",不再是大输出兜底。 |
| **L4(LLM 摘要)** | 降级为最后兜底,且必须结构化为假设树、保留地址。 |

真正让自研工具超过裸 Claude Code 的,是两条 Claude Code 因数据不可寻址而做不到的能力:

1. **子 agent 做独立证伪**(无偏、前置、结构化纠偏);
2. **数据层聚合压缩**(无损、便宜、源头控预算)。

---

## 六、后续可深入方向

- **独立证伪 agent 接口设计**:主 agent 传什么(假设 + 证据 + 查询入口)、子 agent 回什么(反例 / 无反例 / 证据不足)、如何判定"已证伪"——直接决定它能否真正纠偏,设计错了会退化成橡皮图章。
- **假设树的数据结构**:如何强制 LLM 维护 `(假设, 证据, 是否被反例否决)` 而非自由文本,并与 L1/L2/L4 联动。
- **trace 骨架 → 钻取 的预算分层协议**:骨架字段选哪些、钻取触发条件、单 span 日志上限。
